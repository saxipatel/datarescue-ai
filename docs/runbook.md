# Runbook

Commands assume the repository root. All services run under Docker Compose project
`datarescue`.

## Start, stop, status

```bash
make up            # build if needed and start the base stack
make ps            # service status and health
make logs          # follow api, worker, scheduler (JSON lines)
make down          # stop; volumes are kept
```

Startup order: Postgres (healthy) → `migrate` (Alembic + idempotent seed, exits 0) → API,
worker and scheduler → frontend (waits for API health). If `migrate` fails, nothing else
starts. Check it with `docker compose logs migrate`.

## Reset

```bash
make reset         # type 'reset' to confirm; deletes postgres, redis and data volumes
```

This removes all batches, incidents and audit history, then rebuilds and reseeds.

## Migrations

```bash
make migrate                                                  # alembic upgrade head
docker compose run --rm migrate alembic current
docker compose run --rm migrate alembic downgrade -1          # step back one revision
```

New migration (with the dev image, against the dev DB):

```bash
docker compose --profile test run --rm \
  -e DATABASE_URL=postgresql+psycopg://datarescue:datarescue@postgres:5432/datarescue \
  tests alembic revision --autogenerate -m "describe change"
```

Review autogenerated files. Triggers, partial indexes and data backfills need hand edits.

## Responding to an incident

1. **Open it** from Overview or Incidents. Read the summary and the failed rules.
2. **Check the evidence.** `batch_metadata` shows schema versions and the error-code
   breakdown, `duplicate_analysis` shows where duplicate originals live, `sample_records`
   shows redacted payloads, and `pipeline_log` shows the run log.
3. **Read the diagnosis.** Causes are ranked heuristically, so treat them as leads. Check
   the cited evidence. If the incident was opened before a rule change, choose
   **Re-run diagnosis**.
4. **Look at the impact.** The lineage table shows which marts and dashboards consume the
   affected data. Tell the dashboard owners if revenue figures may be off.
5. **Decide:**
   - Not a real problem → **Close as false positive** (justification required). This
     feeds the false-positive count on the Overview.
   - Owned but waiting on someone → **Acknowledge**.
   - Fixable → **Propose repair**, using the recommended action where possible.
6. **Repair.** Run the dry run and compare its counts with the evidence. A steward
   approves, then executes. Keep the idempotency key shown; resubmitting it is always safe.
7. **Verify.** The job page lists each check. If anything remains (for example
   unrepairable currency codes after a case fix), the incident goes back to
   ACTION_REQUIRED and names the remaining issues.

## Recovery job problems

| Symptom | Meaning | Action |
|---|---|---|
| Job `RUNNING`, heartbeat not moving, worker restarted | The executor died mid-run; committed chunks are kept | Resubmit the same idempotency key (UI: **Submit again with the same key**). The retry takes over once the old executor's lock is gone. The scheduler also marks it FAILED after `STALE_JOB_TIMEOUT_SECONDS`. |
| Outcome `in_progress` on resubmit | Another executor holds the advisory lock | Wait. Check `make logs` for the worker that has it. |
| Job `FAILED`, `verification failed` | A check didn't pass; the incident is back in ACTION_REQUIRED | Read the failed check. Nothing was hidden: the before/after checksums and rows written by the job are in `metrics` and in the audit event. |
| `409 idempotency_key_reused` | The key belongs to another proposal | Use a new key for the new proposal. |
| `409 already_executed` | The proposal succeeded before | Create a new proposal if more work is needed. |

## Ingestion problems

| Symptom | Action |
|---|---|
| Batch `FAILED` with `error_message` | Fix the cause (for example the database being down), then `POST /batches/{id}/resume` or the **Resume from checkpoint** button. Processing continues after `processed_count`. |
| Batch stuck in `PROCESSING` | Worker died. RQ retries up to `TASK_MAX_RETRIES` with backoff. After that, resume manually as above. |
| `503 queue_unavailable` on ingest or simulate | Redis is down and the work was not queued. For `/ingestions` the batch is marked FAILED ("not queued"); for `/simulations` the batch stays PENDING. Once Redis is back, resubmit the ingestion (same request key) or resume the batch. |
| `/ready` returns 503 | Look at `checks` to see whether the database or the queue failed. |
| Upload `422` | The message names the problem: missing columns, encoding, extension or size. |

## Scheduler

Runs freshness checks for each enabled source and reaps stale recovery jobs every
`FRESHNESS_CHECK_INTERVAL_SECONDS`. It logs a `maintenance run` line each cycle. A source
that has never delivered a batch is reported as `no_history`, not as stale.

## Analytics

```bash
make dbt           # dbt build: staging view, two marts, 20 tests
```

If `revenue_reconciles_with_staging` fails, the mart is stale or was built mid-ingestion.
Re-run `make dbt`. The marts are fully rebuilt each time, so this is safe.

## Optional services

```bash
make streaming-up
docker compose --profile optional-streaming run --rm stream-consumer \
  python -m optional.kafka.producer --records 2000 --scenario duplicate_event_ids --pct 5
docker compose logs -f stream-consumer
```

Replaying a topic (useful to show idempotency):

```bash
docker compose --profile optional-streaming stop stream-consumer
# wait for the group session to expire (~45 s), then:
docker compose --profile optional-streaming exec redpanda rpk group seek datarescue-ingest --to start
docker compose --profile optional-streaming up -d stream-consumer
```

Airflow: `make orchestration-up`, then open http://localhost:8080. The admin password is
printed in `docker compose logs airflow` on first start. The `datarescue_pipeline` DAG is
paused by default.

## Backups (local)

```bash
docker compose exec postgres pg_dump -U datarescue -Fc datarescue > datarescue.dump
docker compose exec -T postgres pg_restore -U datarescue -d datarescue --clean < datarescue.dump
```
